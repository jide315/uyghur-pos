# 实验、预算与验收计划

记录日期：2026-11-12

补充日期：2026-11-13。以下 A–D 保留为实验方法概览；当前完整阶段划分、交付物及通过条件见 [P0–P8 计划](04-phase-goals-and-acceptance.md)，正式指标以 [评测与决策协议](05-evaluation-protocol.md) 为准。

对应关系：A → P1–P2；B → P4；C → P5；D → P6；新增 P0 任务约定、P3 执行环境、P7 可复现交付、P8 开源与求职展示准备。

本文是拟执行计划，所有结果均待测。当前没有模型分数、性能数据或费用实测。

## 1. 阶段 A：数据和现有基线，先不租卡

1. 检查本机可用 CPU、内存及磁盘，记录环境。
2. 固定 UD 数据版本、Stanza 版本和模型版本，检查许可及获取方式。
3. 检查官方切分、重复或近重复句、缺失标签、长度和词频分布。
4. 用开发集跑通已分词输入下的 Stanza UPOS 评测。
5. 测量 CPU 单句延迟、吞吐、峰值内存、磁盘模型体积及冷启动成本。
6. 输出继续或停止的书面判断。

重复样本先报告；不悄悄更改官方切分。如另做去重实验，应独立命名，并保留标准切分上的可比较结果。

继续条件：基线能够可靠复现，而且发现值得改进的资源开销或具体问题。若开发阶段需要查看测试集质量，限于结构检查；不得用测试表现选择模型或调参。

## 2. 阶段 B：监督训练小模型

- 字符编码用于补充词形信息；小型 BiLSTM 建模句子上下文。
- 首先只做一个规模的模型和一套可运行配置，避免无预算边界的搜索。
- 以训练集构造词表和词频统计，明确未登录词处理。
- 超参数、早停和候选选择仅依据开发集。
- 可增加简单词典／多数标签基线作数据与评测检查，但正式贡献必须与 Stanza 比较。

先在少量数据上验证前向、反向、保存、加载与推理，再开始正式训练。实际显存、耗时必须测量后才能估算总费用。

## 3. 阶段 C：失败观察与针对性改进

先在开发集检查以下分组：

- 训练词表内与未登录词。
- 高频与低频词，长词与短词。
- 各 UPOS 标签，标点与非标点。
- 不同句长。

分组边界在正式比较前固定，词频及是否未登录只依训练集计算。

依据观察选择行动：

| 观察 | 可验证行动 | 检查点 |
| --- | --- | --- |
| 未登录长词错误集中 | 字符编码消融、容量调整 | 改善是否集中于目标组，而非仅总体变化 |
| 小模型与教师输出差异明显 | 在训练集上验证知识蒸馏 | 是否超过同规模监督模型 |
| 资源开销主要来自加载或无关组件 | 缩小部署依赖／仅加载所需组件 | 对基线也做相同合理优化，避免不公平收益 |
| 小模型质量远低于可接受范围 | 调整一次合理容量或停止 | 不通过无限扩大模型掩盖目标失败 |

蒸馏初期只使用训练集。若工具无法稳定提供与词对齐的概率，可明确采用硬伪标签，不能将其描述为软概率蒸馏。不使用测试集教师输出训练。

蒸馏并非必然有益；教师也可能不如金标准。须保留不蒸馏的同规模监督模型作对照。

## 4. 阶段 D：冻结方案后的最终评测

锁定候选、处理规则和验收方式后，再做封存测试集的正式比较。

最终候选和监督对照使用 3 个预登记随机种子，报告均值与波动；若预算不足，减少探索分支。缺少正式种子时交付受限报告，正式压缩验收记为证据不足。

### 质量指标

- UPOS 总体准确率及非标点准确率。
- 各标签 F1 和样本数。
- 未登录词准确率及预先固定的分组结果。
- 原始正确／错误计数、相对基线的变化。

不把字节、字符、子词和 UD 词级指标混用。标注存在争议时记录证据，不凭模型预测更改金标准。

### 部署指标

- CPU 单句延迟 p50／p95、批量吞吐。
- 峰值内存和空进程基线。
- 权重文件、必要附属资源和总部署体积。
- 冷启动与预热后推理分别记录。

固定硬件、CPU 线程、batch size、输入长度分布、预热及重复次数；同一组已分词句子用于双方比较。基线只加载任务所需组件，教师训练开销不计入学生推理，却应单独披露。

## 5. 拟定验收门槛

相对公平配置下的 Stanza 基线：

1. 三种子 UPOS 总体及非标点准确率平均下降均不超过 **1 个百分点**，并满足正式协议的最差种子与 OOV 保护条件。
2. 在开发阶段预选 CPU 推理加速至少 **2 倍**，或峰值内存降低至少 **50%** 为主目标；测试后不能切换主目标。
3. 披露未登录词、非标点、各标签退化和统计不确定性，不能只凭总体达标掩盖明显失效。
4. 他人可以按文档重现数据准备、推理和评测。

数字是当前候选门槛，尚未证实可达。若阶段 A 表明不合理，可在训练和最终测试前书面修订，并解释原因；不看完测试结果再降低门槛。

达到以上指标说明存在工程收益，不自动证明社区有需求。开源贡献报告另行记录实际采用、反馈或上游接受情况，不以 star 数作为唯一证据。

## 6. 预算控制

暂以 **总现金 400 元**为规划上限，待用户明确精确预算；这不是已获授权的付费支出。

| 用途 | 暂定上限 |
| --- | ---: |
| AutoDL GPU 训练与试验 | 250 元 |
| 存储、传输及其他必要费用 | 50 元 |
| 故障与复现实验预留 | 100 元 |

这些是支出上限，不是平台当前报价，也不是预计必须花满。租卡前核对价格、显存和计费方式；用短试跑推算费用并按实际费用记账。优先删减无依据的实验分支，不因“低资源语言”默认需要更大 GPU。

## 7. 风险与退出

| 风险 | 应对与停止条件 |
| --- | --- |
| 基线已有足够轻的实现 | 先核查，缺少空间则不进入训练 |
| 只能击败弱基线 | 不宣称压缩贡献，重新检查比较或停止 |
| 数据小导致收益不稳定 | 报告多种子与样本计数，限制结论 |
| 不懂语言导致错误解释失真 | 依据现成标签和规范；语言学争议留待专家复核 |
| 数据／模型发布许可不明确 | 暂缓相关产物发布，可先交付脚本和来源说明 |
| 训练超过预算 | 保存当前结果、停止付费实验、记录未完成项 |
| 没有实际复用价值 | 保留可复现报告作为求职成果，不夸大开源贡献 |

若压缩未达标，可记录失败实验；只有发现了独立可验证的问题，才转向上游修复，不把“寻找 bug”当成一定能交付的承诺。
